# 开发路线与分工

更新：2026-09-30。阶段编号沿用 DESIGN，实施顺序按当前已有能力安排。
这是依赖规划，不承诺固定工期；每个阶段完成验收后再进入下一阶段。

| 阶段 | 最小交付 | 进入条件 | 工作性质与分工 |
| --- | --- | --- | --- |
| 上线可靠性收口 | 备份可恢复、更新前备份、线上/真机关键旅程有记录 | 用户已部署；先核实现状，已有配置不重建 | 工程任务，可交其他执行模型 |
| M2 写信回信 | 扫描件寄信、回信、未读、作者软删除恢复、旧信迁移工具 | 沿用现有上传和读信能力；发布前完成可靠性收口 | 后端工程 + 常规 React 整合，可交其他模型 |
| M4 漂流瓶 | ≤500 字留言、对方收到、已读、收藏；瓶子视觉反馈 | M2 已读与通知同步方案稳定 | 先做 API，再集中设计海滩/纸条界面；复杂视觉适合由本模型参与 |
| M1 正式地图资产 | Tiled 主岛、图集、碰撞与交互对象、许可/调色板记录 | 已知信箱/日历/漂流瓶锚点；农场扩建前完成 | 场景布局和视觉一致性工作，适合本模型参与 |
| M5 种花送花 | 少量地块、1–2 种花、浇水计天、收获、赠送、对方收到 | 正式交互锚点就绪；共享时区和幂等规则先确定 | 状态机工程与游戏交互分任务；不登录只暂停，不枯萎 |
| M6 氛围与回看 | 从音乐、天气、去年今日、收藏陈列等选一项打磨 | 核心三模块和送花稳定 | 按真实使用反馈选，不默认全部同时做 |

M4 首版收藏先在 React 列表回看，小屋室内珍藏架后续补；因此 M4 MVP 不等于 DESIGN 中完整 M4 里程碑。
如果真机反馈主要问题是画面、可达性或首屏加载，可以将正式地图或针对性的性能修复提前；先测量，不仅因打包警告重构。

## 本阶段边界

当前只实施上线可靠性与 M2。写信第一版使用标题、摘要、扫描件；保留原拆信与翻页。
回信是给对方的新信，不做会话线程；暂不增加富文本、信纸排版工具、背景音乐、实时联机与完整离线草稿。
旧信源缺失只阻塞真实导入验收，不阻塞新信闭环；完整 M2 的旧信迁移项仍保持未完成。

## 任务分配方法

1. 给执行模型一个明确任务编号，连同 [M2 计划](NEXT_STAGE_M2.md) 与对应验收条目。
2. 工程与常规前端优先复用已有实现；产品规则或跨层契约修改须同步文档。
3. 每包独立提交、检查并交接；前一包的接口先稳定，再接前端。
4. 将复杂前端集中到明确的视觉任务：漂流瓶海滩与开瓶、正式地图与手机 HUD、送花/收花仪式。
5. 复杂视觉任务开始前，先提供实际页面、素材与接口数据，保留时间设计完整交互，不在后端工程包中顺手大改视觉。

## 阶段完成判断

实现不等于发布。代码合并后，依次满足本地自动检查、浏览器双账号旅程、可用设备真机记录和生产发布条件。
无法执行的项目记为未验证，并列出所缺条件；新功能的线上检查使用明确标记的测试数据，不修改既有真实内容。
