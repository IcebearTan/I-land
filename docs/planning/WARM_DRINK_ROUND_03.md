## 体验与范围

进屋 → 到小料理台发起制作 → 一人或两人明确加入 → 各自选杯型/配料 → 控温与搅拌合作 → 分杯、给配方起名 → 领取/递杯/碰杯 → 可查看这次作品和真实制作人。

- 一张小料理台、一个热可可基础配方、三种配料（棉花糖/可可粉/肉桂）、两种杯型（奶油/青绿），基础材料直接供应。
- 一人控温，一人搅拌；搅拌对温度有影响，在适宜温区持续搅拌才增长进度。能够交换工位、暂停，一人可顺序操作两个工位。
- 目标是一小局宽松的合作，不用密集连点。越过温区只暂停进度，不烧毁物品或扣分；离线/后台不丢作品。
- 本轮复用客厅，不建完整厨房，不做农场、货币、通用背包、照片保存或自由走动联机。
- 制作结果包含实际制作人、真实日期、杯型、配料和配方名；可在本轮简短作品面板回看。未来接日历，但不虚构已完成 MEMORY-01/02。

## 权威状态与可靠性

1. 复用真实 interior 房间身份和租约；料理是客厅内的固定工位活动，不能伪造同伴或把本地模拟作为联机交付。
2. 整合者先在自己的评估目录写 `PROTOCOL.md`：状态、动作、默认节奏与数值、断线/恢复、角色交换、持久化、结果幂等；接口稳定后再连接 UI。UI 先做受控展示组件，避免争改公共类型。
3. 温度/进度由服务端推进和校验，客户端只发操作意图；不能自报时间增量、进度或“制作成功”。页面后台/失联释放持续输入，不允许旧按住指令永久生效。
4. 状态包含准备、制作、暂停、分杯、完成；阶段和必要恢复信息走 REST 保存，房间快照推送确认状态。重连/重启从可解释的安全状态继续，不补算离线刷进度。
5. 同一局完成只产生唯一配方记录与两杯成果，事务/唯一约束保护重试与竞争。杯子预留给两位固定身份；只有实际操作的人列为制作人，一人制作不能伪造另一人参与。
6. 递杯先支持把对方预留的杯子交到对方手中，需对方回应；取消/离开后杯子仍可领取。碰杯是两位真实在场且有杯子的共同动作。不要扩成通用物品交易系统。
7. 做料理与坐沙发在同一时刻互斥；只绘制经确认工位上的远端人物。没有位置同步时不虚构对方从门口走到料理台的轨迹。
8. 个人声音、减少动态与身份稳定规则保持。新表按项目规范放 models.py，新 REST 路由挂载 main.py，前后端只经 EventBus 通信。

- 两个独立 Cookie 会话：先后加入、两种工位确实互相影响、交换、暂停/继续、完成与配方保存。

- 料理台不挡门/沙发/炉火，退出料理能安全返回走动/坐下；只检查此次直接受影响的原房间流程。
