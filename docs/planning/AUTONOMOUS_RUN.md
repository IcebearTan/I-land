## 验收规则（覆盖旧计划）

1. 不生成或验证交付 SHA-256，不重算旧清单。READY 保留版本、路径、尺寸/接口、已做检查、限制；整合时检查实际文件存在、接口/尺寸相符、变更和效果。
2. 不跑全量回归：不得执行 pytest tests/ -q、node --test tests/*.test.mjs 或变相覆盖全部测试的脚本。选明确的相关文件/用例；必要类型检查/构建保留。
3. 主对话先审阅现成有效证据、改动和实际输出；只有新变更、失败或未解决疑点才补相关测试。不要为了“主对话再确认”重复同一整套检查。
4. 当前轮的重点是字体与人物比例、关键交互、真实双会话座位/电视状态、直接受影响的场景交接。只选本轮涉及的关键流程，不每轮完整遍历所有旧功能。
5. 视觉交付要实看图；需要浏览器证明的流程保留实际截图与结果。测试数据全部隔离。没有证据不宣称通过，静态示意不是在线双人证明。
6. 本地验收通过才可进入下一轮；真机/线上条件缺失单列限制，不冒充完成，也不阻塞独立的本地开发。
7. 验收失败就定向返工当前轮，修复后只复验失败项与直接影响范围。

## 每次监视流程

1. 先读本文件及 `AUTONOMOUS_STATE.json`，检查是否已停止、当前轮次和上次游标；检查任务/自动执行状态有无额度耗尽或用户停止记录。
2. 用 wait_threads 的紧凑快照检查下列现有对话。没有变化、没有可执行事项时结束本次检查，避免反复读取历史或重复派发。
3. 部分交付完成时核对 READY 与文件归属，通知整合者按冻结约定接入；不提前开始有依赖的下一轮。
4. 本轮完成后按上述规则验收，更新 CURRENT_STATE / NEXT_STAGE_COOP / 轮次评估。在所有相关写入停止后仅暂存明确属于该包的文件，按包本地提交。
5. 验收通过后从路线选择下一个有完整使用过程的功能，拆出互不覆盖的设计/素材、逻辑、整合任务，发给现有对话启动。下一轮优先合作暖饮（PLAY-01/02、ITEM-01、SOCIAL-02），再接合照/共同记忆/陈列；不要只做更多外观而停止新增玩法。
6. 保存当前轮次、交付/问题、已做检查、提交、下步、游标。普通未变化不发送重复状态；完成验收、下一轮已启动、真实阻塞或额度停止等有意义变化才报告。

## 停止与额度边界

- 只用平台实际暴露的状态判断额度；看不到余额就不编造剩余额度或保证能运行多久。
- 一旦工具、任务或自动执行明确返回额度/使用上限耗尽：记录 quota_exhausted，停止派发并暂停本自动任务；能通知仍运行的任务时发出停止指令并保存交接。
- 若额度使当前自动检查本身无法运行，下次可运行时先检查上一轮失败/额度记录；若曾耗尽，本次过夜批次保持停止，不因自然恢复而重新开工。
- 不通过缩短轮询、反复重试额度错误或使用重置卡续跑。短暂网络错误与额度错误分开处理。
- 若用户停止、出现需要用户操作的实际阻塞，或确认路线范围已经全部完成，记录原因并停止/暂停；不得越过权限或伪造验收来继续。
- 本地任务需要电脑与 Codex 可运行；电脑休眠/应用退出/额度不足时不保证后台执行，保留进度便于恢复。
