## 原问题

1. `PRAGMA integrity_check` 只调用 `fetchone()`，既不判断是否为 `ok`，也不检查完整结果；
   SQLite 能打开、返回错误行但不抛异常的损坏索引会被接受。
2. 清单只做 JSON 解析，`app`、时间、大小、附件数均未验证；缺字段可能在目标已被改动后才报错。
   旧清单没有文件校验和，数量相同的照片替换/损坏无法识别。
3. 原实现只暂存数据库探针，随后先移走旧目标，再从源复制数据库和附件；
   复制失败会留下不完整目标，也没有发布失败的自动回退。实际流程不符合原注释的“原子替换”描述。
4. 回退目录名只精确到秒，`shutil.move` 遇同名已存在目录可能产生嵌套；
   源/目标互相包含、符号链接、旁路 WAL/SHM 和挂载点缺少限制。
5. 创建备份时缺数据库会写空文件，缺附件目录会生成空目录，仍打印成功；
   中途失败可能留下外观类似正式备份的半成品。
6. 原正式恢复说明建议直接对数据卷挂载目录操作，未说明 `/data` 无法按普通目录重命名、
   备份位于目标内部会冲突，也没有完整的配置切换/失败处理步骤。

## 行为变更与未验证范围

- 正式备份目录名增加随机后缀，避免同秒冲突；仍以 `iland-backup-` 开头。
  如果部署有依赖旧完整命名格式的外部脚本，需要核对，当前仓库未发现此类调用。
- 数据源缺失不再生成“空备份”；全新部署应先正常初始化。合法已初始化库配空 uploads 仍支持。
- 恢复目标必须停写，并与备份目录互不包含；挂载根目录应改用卷内独立子目录和配置切换。
  两次目录改名之间存在短暂目标路径缺口，不支持同时恢复同一目标或在线热切换。
- 回退目录保留整个旧目标，含 WAL/SHM 与额外文件；不自动清理、合并或删除旧数据。
  正常异常可回退；断电、强杀、文件系统损坏及 fsync 持久性未实测，也不承诺自动恢复。
- 故障注入验证的是复制/重命名错误处理，没有实际填满磁盘、改变真实权限或损坏文件系统。
  挂载点拒绝使用模拟测试；Docker named volume、跨设备挂载、服务器配置切换与线上内容未实跑。
- v2 哈希可检出清单生成后的字节/路径损坏，不是真实性签名；清单和数据一起被改写仍需可信副本。
  旧格式没有哈希，只能核对库完整性/大小、附件数与结构，不能保证照片未被同数量替换。
- 未扩展业务层引用审计、图片解码检查或数据库迁移兼容检查；备份前就存在的缺图/错误引用不会由哈希补回。
  原信件、照片和新旧应用版本兼容性需独立实例人工核对。当前附件无自动物理删除；将来引入清理时须重新评估在线备份一致性。
- 运维步骤已经补全，但本包没有演练生产卷，也没有验证线上定时备份、保留周期、异地副本和告警。
