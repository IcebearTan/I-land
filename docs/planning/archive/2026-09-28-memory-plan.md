## 1. 阶段目标

让两人能够放心地在手机上保存照片与文字，并在灯塔日历里共同回看。

本阶段完成三件事：

1. 修复私人内容访问、首次部署与资源托管问题，建立改密和备份恢复流程。
2. 建立可供记忆卡和未来扫描件写信复用的图片上传能力。
3. 完成每日记忆卡的创建、查看、修改、删除恢复与月历关联。

核心验收旅程：小熊登录 → 选择某一天 → 上传照片并写下描述 → 保存 → 她登录 → 在同一天看到完整记忆 → 刷新后内容仍在。

## 4. 用户体验设计

### 4.1 记下一天

1. 从灯塔或现有日历快捷入口打开日历。
2. 选择日期，点击“添加记忆”，与“新建节日”明确区分。
3. 添加照片或描述，按需填写标题、心情、天气和地点。
4. 预览照片、调整顺序，等待上传完成后保存。
5. 保存成功后返回所选日期，显示新增记忆并更新月历缩略图。

照片与描述至少填写一项，其余信息可选；未填标题时界面使用日期和描述摘要呈现，避免强迫用户取标题。

### 4.2 回看与共同编辑

- 同一天允许多条记忆，保留创建者和创建时间。
- 月视图显示一张代表照片与内容数量，限制贴纸数量，避免挤压日期。
- 日视图分别展示纪念日和记忆卡；照片支持大图查看和逐张切换。
- 两人均可查看和编辑共同记忆，保留最后修改者与修改时间。
- 编辑期间对方已更新时，提示冲突并保留当前输入，不静默覆盖。
- 删除使用二次确认，进入“最近删除”；本阶段建议保留 30 天恢复窗口。
- 恢复窗口内不物理清理关联照片；过期清理流程另行明确后再启用。

### 4.3 手机与异常状态

- 以 375px 宽度设计单列布局，覆盖手机键盘弹出、长文本和多图场景。
- 面板打开时暂停角色输入，照片滑动和表单操作不触发走位。
- 每张照片分别显示上传进度或状态，失败后可单独重试或移除。
- 保存期间避免重复提交；网络重试也不能生成重复记忆。
- 保存失败或会话过期时保留当前页面内的输入，允许重试或重新登录。
- 当前页面保留不等于刷新后恢复；本阶段不承诺未保存内容在刷新后仍存在。
- 关闭有未保存内容的面板时提供确认；成功状态仅在服务端确认后显示。

## 5. 开发任务拆分

### P0-A：私人内容与身份校验

现状依据：`backend/app/routers/letters.py` 的读取接口未要求登录，创建接口接受客户端作者；`world.py` 的读取接口未要求登录；上传目录采用公开静态挂载。

- [x] 为私人内容的列表、详情和世界状态读取统一加入身份校验。
- [x] 图片原件、展示图、缩略图使用受保护的访问方式，不能靠隐藏页面保护内容。
- [x] 寄信作者由当前登录账号确定。
- [x] 明确信件现有删除权限；建议仅作者可删，避免误删对方来信。
- [x] 附件通过服务端生成的标识关联，不接受任意磁盘路径或任意外部 URL。
- [x] 增加未登录读取、身份冒用、越权访问和无效附件引用测试。

验收：未登录直接请求接口和附件均无法获得私人内容；登录后两人能够查看共享记忆和合法附件。

### P0-B：部署与首次启动

静态分析发现：Docker 将前端构建产物复制到 `/app/frontend/dist`，后端在当前容器目录结构中会查找 `/frontend/dist`。上传目录挂载判断早于 lifespan 内的目录创建，首次启动可能缺少资源路由。

- [x] 统一容器内前端构建产物位置与后端托管路径。
- [x] 统一数据目录初始化和资源路由注册时机。
- [ ] 验证全新数据卷首次启动、已有数据卷升级、容器重启三种情况。
- [x] 验证前端首页、登录、API 和附件在生产托管模式下均可访问。
- [ ] 验证 HTTPS 部署下的 Cookie 配置，并保留本地开发可用性。

验收：全新部署无需手动建立上传目录或额外重启，即可登录、上传并查看照片。

### P0-C：改密与备份恢复

当前种子逻辑只创建不存在的用户，修改 `ILAND_SEED_USERS` 不会更新已有账号密码。

- [x] 提供最小改密入口：校验旧密码、设置新密码、使旧会话失效。
- [x] 说明首次部署设置密码与已有账号改密的区别。
- [x] 制定 SQLite 一致性备份方案，避免将运行中的主数据库文件单独复制视为完整备份。
- [x] 将数据库、关联附件和恢复说明作为同一套备份内容。
- [x] 明确备份时的写入协调方式，确保数据库引用与附件一致。
- [x] 建议每天备份、升级前额外备份；保存位置与保留周期在实际部署时配置。
- [x] 在独立临时目录演练恢复，验证记录、原图和缩略图完整。

验收：新密码可以登录、旧密码和旧会话失效；恢复出的环境可打开记忆与信纸。恢复演练不得覆盖现有真实数据。

### P1-A：共用图片上传

- [x] 新增上传接口及附件元数据，记录上传者、类型、尺寸、文件位置和创建时间。
- [x] 使用 Pillow 验证实际图片内容，生成展示图与缩略图，统一方向并处理透明通道。
- [x] 确定原件保留策略；对用户可访问的派生图片移除不必要的 EXIF 定位信息。
- [x] 首版支持 JPEG、PNG、WebP；实际验证手机照片选择器行为，HEIC 无法处理时给出明确提示。
- [ ] 建议首版每条记忆最多 9 张、单文件最多 20MB；同时设置解码像素上限，最终数值经真机验证调整。
- [x] 前端支持预览、排序、移除、上传状态和单张重试。
- [x] 请求封装支持 multipart，不把图片上传误设为 JSON 请求。
- [x] 保存记忆前核实全部附件上传成功；失败时不产生引用缺失图片的正式记录。
- [x] 区分临时附件与已关联附件，登记未提交附件供后续清理，不在本阶段贸然批量删除历史文件。

验收：正常照片可显示缩略图和大图；无效、超限文件有明确错误；弱网重试不重复关联附件。

## 6. 数据与架构约束

- Phaser 与 React 继续仅通过 `frontend/src/game/EventBus.ts` 通信。记忆卡属于 React 面板，本阶段无需让 Phaser 接触表单内部状态。
- 所有持久化通过后端 REST API；不使用 localStorage 保存记忆、草稿或偏好。
- 新表加在 `backend/app/models.py`，新路由放在 `backend/app/routers/`，由 `main.py` 挂载。
- 独立内容留在专属表中，不把照片和记忆正文堆入 `world_state`。
- 附件模型记录实际文件信息，记忆按有序附件标识关联；兼容现有 `photos_json` 的迁移方式在实施时明确。
- 记忆日期表示用户选择的日历日，不做 UTC 偏移；创建、修改等时刻统一存储并按客户端显示。
- 本阶段沿用已有纪念日本地日期规则；共享时区和农场每日边界在相关阶段统一设计。
- 美术沿用 DESIGN.md 最新修订；正文颜色、动效透明度和 `prefers-reduced-motion` 遵守现有约定。
- 不删除、不提交 `backend/iland.db`、`backend/uploads/` 及其中的真实内容。
